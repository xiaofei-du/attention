## 當前第一步：本輪工作摘要

每個 session 在這一輪結束時，依內容與使用者的多任務情境，選擇直接朗讀原話或產生口語摘要。規則寫在 `summary-prompt.txt`，由每輪 hook 自動加入，不需要獨立 skill，也不需要追蹤「上次匯報」的位置。

由 AI 判斷要不要摘要、多少內容才說得清楚。沒有 160 字的分類切線，約 30 秒只是參考。簡潔自足的回覆直接读原話；需要提示任務背景時，短答案也可以選摘要。程式碼、表格、連結及路徑仍需 plain spoken summary。

使用者在多個 session 間工作；摘要先用已知專案、功能或具體問題喚起 context，提示 goal，再說本輪 progress 與 what's next。只補足辨識這個任務所需的背景，不重述專案歷史、不猜名稱或目標。沒有下一步或決策則留空。

語言跟隨正常回覆及使用者偏好。原 session 以本機命令暫存摘要，程式尊重此選擇，不會因正常答案短而忽略它。未提交時才尝試直接朗讀；程式保留格式、共用大小上限與最長播放時間的保護。

新安裝預設開頭為「hey sunshine」；升級保留已保存的文字、音效或空開場；使用者可透過 agent 呼叫 set_start 設定完整開場，一旦保存就固定使用，直到明確要求更新；使用「我／你」自然對話，不使用報告式標題。稱呼由播放程式加入，摘要模型不重複加入。

摘要按以下順序自然連成一段：

1. **Why we do this：** 先點明這是哪個專案、功能或問題，再說它要達到的目標。
2. **What we have done：** 這輪實際做了什麼，以及主要結果。
3. **What's next or decision to make：** 接下來要做什麼，或需要使用者決定什麼。

不用念出 Why／What／Next 標題。已完成、僅有計畫、已驗證與尚未驗證的狀態要如實表達；如果沒有下一步或待決策事項，不要為了填滿格式自行創造工作。

候選摘要指令：

> 請跟隨正常回覆的語言，寫一段適合朗讀約半分鐘的本輪工作摘要。考慮使用者正在多個 session 工作，先說這是哪個任務、目標是什麼，再說我這輪實際完成了什麼及結果，以及真實下一步或待決策事項。長度按資訊量調整，不湊滿半分鐘。依據本輪實際紀錄，用「我／你」自然對話，不列工具日誌、不堆檔案路徑、不重述整個專案歷史，也不要捏造已完成事項或待決策事項。稱呼由播放程式加入。實際輸出協定見 summary-prompt.txt。

示例（假設性的工作內容）：

> hey sunshine 你之前提到，使用者登入後還是會被登出，希望登入能保持穩定。我這輪修正了登入狀態的更新邏輯，也測過登入過期和重新登入的情況，測試都通過了。修改目前在本機，還沒有上線。接下來會到測試環境確認；通過後，再依你授權的發布範圍處理上線。

短回覆驗收看是否只朗讀原話、稱呼僅加一次；長回覆驗收看摘要是否忠實、有用、適合朗讀。兩者共用已接通的通知隊列和媒體降音量。

## 已確認需求

- 使用者接受按鍵開始說話，可以看螢幕，不要求對方用語音回答。
- 第一個工作項目是以本輪摘要替換現有完成通知；其他任務的通知仍須排隊，不自動打開麥克風。
- 由原 session 按資訊量及多任務上下文決定直接讀或總結；簡潔答案不重複總結，摘要先喚起任務及目標。程式只保留格式與過長保護。
- 播報時降低同一輸出裝置上的其他媒體，播完恢復；使用者已授權本機系統音訊處理，且不儲存或上傳捕獲的音訊。
- 使用者用語音輸入，原任務以文字回覆；可以多輪繼續。
- 正在處理 A 時，B、C 完成只安靜入隊，不搶焦點或切換任務。
- 正在看 A 的文字回覆也屬於處理 A；錄音停止不等於可以切換到 B。
- 保留原始 session、工作環境、模型與上下文。
- 執行時機由使用者指令和原生 agent 決定，不強制等到「over」。
- Codex 與 Claude Code 共用產品方向，第一版先驗證 Codex。

## 尚待選擇的送出方式

已向使用者詢問：每輪可以再按一次鍵結束並送出，還是說完自動送出、繼續聽下一句。此項尚未取得回答；不把任一選項寫成已確認需求。

| 方式 | 測試重點 |
|---|---|
| 按鍵控制每輪 | 按鍵開始、說話、按鍵結束並送出、看文字回覆；核對原生是否還需要另外按 Enter |
| 一次開啟、持續交談 | 自動辨識每句結束並送出，繼續等待下一輪；不把一般聽寫冒充已具備的連續對話能力 |

不需要語音回答，並不自動代表使用者接受每輪手動送出。先確定這個差別，避免選錯輸入方式。

## 通知摘要之後：語音輸入驗證

完成通知摘要與通知接入後，再測 Codex 的原生聽寫，在同一個現有任務完成三輪「說話 → 送出 → 看文字回覆」。把實際需要的按鍵數量、焦點條件與送出方式記清楚。

如果原生功能已滿足操作需求，第一個成果可以是設定與操作方式。自製程式只處理測試後仍存在的缺口。

## 原生能力證據

- Codex 所在的 ChatGPT 桌面 app：官方文件描述輸入框可見時按 `Ctrl+Shift+D`，語音會轉成輸入框內的文字，讓使用者在送出前檢視與編輯。這證實聽寫入口，不證實同一按鍵可以停止並送出，也不證實全域或連續自動送出。[官方聽寫文件](https://learn.chatgpt.com/docs/prompting#use-voice-dictation)
- Claude Code CLI：官方文件描述 `/voice tap` 可按一下開始、再按一下停止並送出。自動送出有至少三個詞的門檻；較短內容只放入輸入框。這是 CLI 證據，不能直接套用到 Claude 桌面 Code 介面。[官方文件](https://code.claude.com/docs/en/voice-dictation#tap-to-record-and-send)
- 中文、英文混用與短句修正需要實測；不能因為有麥克風按鈕，就假設辨識和送出符合需求。
- 本環境的 computer-use 工具拒絕操作 Codex 自身，因此沒有完成本機聽寫或快捷鍵測試；不能繞過此限制。

## 後續驗證：同一任務的三輪語音輸入

- [ ] 使用已指定的測試任務，確認输入框和目前 session 身分。
- [ ] 透過原生入口開始聽寫，說「請只用文字回覆 NKC-TEXT-01，不要修改檔案」。
- [ ] 記錄停止錄音、轉寫完成和送出訊息各需要哪些操作；只出現在輸入框不算已送出。
- [ ] 確認訊息與回覆出現在同一個原任務，對方保持文字輸出。
- [ ] 第二輪說「改成 NKC-TEXT-02」，確認保留同一段對話上下文。
- [ ] 第三輪測試短句和中英文混合用語，確認不會因自動送出門檻或辨識差異留下未送出的訊息而沒有提示。
- [ ] 在允許的環境測試輸入焦點改變的情況，不能把語音文字送到另一個任務或其他輸入框。
- [ ] 依使用者選擇的送出方式核對驗收結果；原生需要額外操作時如實記錄缺口。

**通過條件：** 不需打字，按鍵數量符合使用者選擇，連續三輪都送到原任務並在螢幕看到文字回覆。此測試不需要即時語音輸出 API 或外部 app-server 控制。

## 待處理隊列仍須保留

隊列和「目前正在處理哪個任務」分開。麥克風是否錄音不能用來判斷整段互動是否結束。

- 完成事件使用平台、host、原始 session ID 和 turn/event ID 識別及去重。
- 使用者開始處理 A 後，A 保持選定，跨越錄音、送出、等待回覆、看文字和下一輪輸入。
- B、C 完成只安靜入隊，不自動改變畫面或語音輸入目的地。
- 不因短暫沉默、錄音停止或 A 回覆完成而自动取下一個任務。
- 需要明確的「結束目前互動／下一個任務」操作。先前提出的「over」可以保留為候選，但純聽寫可能只是把它當成普通文字；控制指令的接法需要驗證，不能假設它原生會釋放隊列。
- 是否使用額外按鍵或語音指令切換待處理任務，在第一個輸入流程驗證後選定；不能默默增加滑鼠或打字步驟。
- 選擇下一個任務前確認目的地；轉寫尚未送出時，不能把草稿帶到別的任務。
- 對話中的工作指令由原生 agent 處理；隊列程式不重播對話或重送一次。

**隊列驗收：** A 錄音時、A 等待回覆時、使用者閱讀 A 回覆時，B、C 完成都不打斷；只有使用者明確結束或切換後才處理下一個。

## 後續順序

1. 定好 Why → What → Next／Decision 的本輪摘要，目標約半分鐘。
2. 將摘要接到任務完成通知，遵守隊列不打斷規則。
3. 確認每輪送出方式，驗證 Codex 原生聽寫與文字回覆，只補必要缺口。

5. 需要時再做安裝與 plugin 包裝。
